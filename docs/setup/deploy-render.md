# Deploying INFRAOS to Render

Two Render **Web Services** from one GitHub repository (npm workspaces): the **API** (Express) and the **web app** (Next.js). The database stays on **MongoDB Atlas**. The optional **AI service** (FastAPI, `infraos-ai` in `render.yaml`) is described in the section at the end of this guide.

```text
Browser ──► infraos-web (Next.js)  ──► infraos-api (Express) ──► MongoDB Atlas
              onrender.com               onrender.com               (GridFS stores files)
```

> Demo and seed data is synthetic. This guide is for a demo or staging deployment. It is not a production-readiness sign-off.

## 0. Before you start

1. The code you deploy must contain the Render fixes: `npm start` for the API runs `tsx src/server.ts` (the compiled `dist` build cannot load the shared package), and `render.yaml` exists. Both are in the repo root and `apps/api/package.json`.
2. Pick the branch Render deploys. Use `main` once the work is merged, or the feature branch for a first trial.
3. Have ready: a GitHub account connected to Render, and your Atlas connection string for the database you want to use.

## 1. MongoDB Atlas

1. **Network Access:** add an IP access entry that allows Render. The simplest for a demo is `0.0.0.0/0` (allow from anywhere). Tighter: use the outbound IP ranges Render lists on each service's *Connect* menu.
2. **Database user:** use a user restricted to the one database.
3. **Database name:** you can reuse `infraos_dev` (it already holds the demo data). Use a different name such as `infraos_demo` for a clean database, then seed it (section 6).
4. Copy the connection string. URL-encode special characters in the password.

## 2. Push the code

```powershell
git push origin <your-branch>
```

## 3. Create the services with the Blueprint (recommended)

1. Render dashboard, then **New**, then **Blueprint**.
2. Connect the repository and choose the branch.
3. Render reads `render.yaml` and shows two services: `infraos-api` and `infraos-web`.
4. Fill in the prompted values (`sync: false` ones):

| Service | Variable | Value |
|---|---|---|
| infraos-api | `MONGODB_URI` | your Atlas connection string |
| infraos-api | `MONGODB_DB_NAME` | for example `infraos_dev` |
| infraos-api | `FRONTEND_ORIGIN` | the web URL (you will not know it yet: enter a placeholder such as `https://infraos-web.onrender.com`, then fix it in step 5) |
| infraos-web | `NEXT_PUBLIC_API_BASE_URL` | the API URL (placeholder `https://infraos-api.onrender.com`, fix in step 5) |

`ACCESS_TOKEN_SECRET` and `REFRESH_TOKEN_SECRET` are generated for you. They are different random values.

5. Click **Apply**. Both services build.

### Manual alternative (no Blueprint)

Create two Web Services from the same repo with these settings:

| Setting | API | Web |
|---|---|---|
| Root directory | *(empty)* | *(empty)* |
| Runtime | Node | Node |
| Build command | `npm ci` | `npm ci && npm run build -w @infraos/web` |
| Start command | `npm run start -w @infraos/api` | `npm run start -w @infraos/web` |
| Health check path | `/api/v1/health` | *(none)* |
| Instance type | Free is fine | **Starter or larger** (Next.js build runs out of memory on 512 MB) |

Add the environment variables from section 4.

## 4. Environment variables

**infraos-api**

| Key | Value |
|---|---|
| `NODE_VERSION` | `22` |
| `NODE_ENV` | `production` |
| `API_PREFIX` | `/api/v1` |
| `FRONTEND_ORIGIN` | exact web origin, `https://<web>.onrender.com`, **no trailing slash, no path** |
| `MONGODB_URI` | Atlas connection string |
| `MONGODB_DB_NAME` | database name |
| `ACCESS_TOKEN_SECRET` | random, 32+ characters (generated by the Blueprint) |
| `REFRESH_TOKEN_SECRET` | random, 32+ characters, **different** from the access secret |
| `ACCESS_TOKEN_TTL` / `REFRESH_TOKEN_TTL` | `15m` / `7d` |
| `LOG_LEVEL` | `info` |
| `STORAGE_PROVIDER` | leave empty (GridFS) |
| `DOCUMENT_MAX_FILE_MB` | optional, for example `10` |

**infraos-web** (these are baked in at **build** time)

| Key | Value |
|---|---|
| `NODE_VERSION` | `22` |
| `NEXT_PUBLIC_API_BASE_URL` | API origin only, `https://<api>.onrender.com`, **no `/api/v1`** |
| `NEXT_PUBLIC_AUTH_LOGIN_ENABLED` | `1` |
| `NEXT_PUBLIC_MAP_STYLE_URL` | optional HTTPS map style |

Never put database, JWT or storage secrets into a `NEXT_PUBLIC_*` variable.

## 5. Wire the two services together

Cross-site cookies need exact origins, so do this once both URLs exist:

1. Open `infraos-api` and `infraos-web` and note their URLs (`https://infraos-api.onrender.com`, `https://infraos-web.onrender.com`, or whatever Render assigned).
2. `infraos-api`: set `FRONTEND_ORIGIN` to the **web** URL. Save (Render redeploys).
3. `infraos-web`: set `NEXT_PUBLIC_API_BASE_URL` to the **API** URL. Then **Manual Deploy**, then **Clear build cache & deploy** so the value is built in.

The refresh cookie is `HttpOnly; Secure; SameSite=None`, so both services must be served over HTTPS (Render does this by default).

## 6. Data

- **Reusing `infraos_dev`:** nothing to do. The demo data is already there.
- **A new empty database:** run these from your own computer with `apps/api/.env` pointing at that database (the seed commands refuse `NODE_ENV=production`, so run them locally with `NODE_ENV=development`, and the database name must be `infraos_dev` or `infraos_test`):

```powershell
npm run db:seed:core
npm run db:seed:demo
npm run db:seed:verify
```

- **Existing database from before Batch 08:**

```powershell
npm run db:sync:document-permissions -- --apply --confirm-db=<MONGODB_DB_NAME>
npm run db:backfill:documents -- --commit
```

- **A login:** the demo fixture users cannot sign in. Register an account in the app, or set a password for an existing one:

```powershell
npm run db:set-password -- <email> <new-password>
```

## 7. Verify the deployment

| Check | Expect |
|---|---|
| `https://<api>/api/v1/health` | `200` |
| `https://<api>/api/v1/ready` | `200` (503 means MongoDB is not reachable: check Atlas network access and `MONGODB_URI`) |
| `https://<web>/` | landing page |
| Sign in at `https://<web>/login` | lands on `/dashboard` |
| Projects, InfraMap, DocTrace | data from Atlas appears |
| DocTrace upload | a small PDF uploads and downloads |

## 8. Troubleshooting

| Symptom | Fix |
|---|---|
| API build or start fails with `ERR_MODULE_NOT_FOUND ... shared-types` | The start command must be `npm run start -w @infraos/api` (it uses `tsx`). Do not use `node dist/server.js`. |
| `/ready` is 503 | Atlas Network Access does not allow Render, wrong `MONGODB_URI`, or special characters in the password are not URL-encoded. |
| Login fails or loops back to `/login` | `FRONTEND_ORIGIN` is not the exact web origin, `NEXT_PUBLIC_API_BASE_URL` points at the wrong place or was changed without a rebuild, or `NEXT_PUBLIC_AUTH_LOGIN_ENABLED` is not `1`. |
| Browser console shows CORS errors | Same as above: the origin must match exactly (scheme, host, no trailing slash). |
| Web build is killed or runs out of memory | Use the Starter instance type or larger for `infraos-web`. |
| First request takes ~30 s | Free instances sleep after inactivity. Upgrade the API instance, or call `/api/v1/health` to wake it before a demo. |
| Uploads fail with "storage unavailable" | `STORAGE_PROVIDER` must be empty (GridFS) and `/ready` must be 200. |
| Rate limit (429) behind Render | The API sets `trust proxy` only when `NODE_ENV=production`; make sure it is set. |

## 9. Updating the deployment

Push to the deployed branch. Render redeploys automatically. If you change a `NEXT_PUBLIC_*` value, trigger a web redeploy (with *Clear build cache*), because those values are compiled into the build.

When you continue development, keep deploying from `main` (merge reviewed work into `development`, then into `main`) so the live demo only changes when you intend it to.

## Optional: AI service (Phase 10 Batch 09)

1. **Qdrant Cloud**: create a free cluster, copy its HTTPS URL and an API key (never commit them).
2. Render creates `infraos-ai` from `render.yaml` (Python, `rootDir apps/ai-service`, build `pip install .`, start `uvicorn app.main:app --host 0.0.0.0 --port $PORT`, health `/health`). Set `AI_INTERNAL_SECRET` (random, 48+ bytes), `OPENROUTER_API_KEY`, `QDRANT_URL`, `QDRANT_API_KEY`; `AI_EMBED_MODEL` defaults to `baai/bge-m3`.
3. On `infraos-api` set `AI_BASE_URL` to the `infraos-ai` origin and the **same** `AI_INTERNAL_SECRET`. Without them the API boots normally and DocTrace reports AI processing as unavailable.
4. Free instances sleep; the API job runner wakes the service (up to about 70 s) and retries with backoff. Run `npm run ai:smoke` locally against the deployed URL to verify.
5. Existing databases: run `npm run db:migrate:document-chunks` (dry run first, then `-- --commit`) and `npm run db:sync:document-permissions` (dry run, then `-- --apply --confirm-db=<name>`) once, after owner approval.
